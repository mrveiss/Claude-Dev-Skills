When to use: Building or refreshing the map for a commit; running the scripts; the safety guarantees.

# /claude-dev-skills:code-library regenerate

```bash
git -C <repo> archive <commit> | tar -x -C <src-dir>          # read from the commit, not the working tree
python3 -I <plugin>/skills/code-library/scripts/index.py <src-dir> <map> --commit <sha> [--commit-date YYYY-MM-DD] [--config code-classes.json] [--issues gh-issues.json]
python3 -I <plugin>/skills/code-library/scripts/forks.py <src-dir> <map> --commit <sha> [--audit canonical-audit.json] [--issues gh-issues.json] [--config ...] [--min-nodes 30] [--all]
```

- Both take `<repo>` as a path to files; inside a git checkout `--commit` defaults to `HEAD` (read with `git log`, which runs no repo code).
- `--issues` is a `gh issue list --state all --json number,title,body,state` dump you saved. In `index.py` it limits the cited `#N` on cards to open issues; in `forks.py` it matches issues to classes.
- Same commit and config give byte-identical output (sorted everywhere, no wall-clock time); unchanged files keep their mtime; stale generated files in a written directory are pruned by their marker. Regenerate when the base branch moves.
- Parsing fans out over processes (`multiprocessing`), so a large repo maps in tens of seconds.

Guarantees (each pinned by a test): the target is never imported, executed or put on `sys.path` (a fixture that raises and writes a file on import stays untouched); `<map>` inside `<repo>` is refused with exit 2, as is any written directory that resolves into it (a symlinked `library/` or subdirectory), checked before the first write; `--commit` must be a hex SHA or ref name (never an option); the repo tree is byte-identical before and after a run; files that fail to parse, or nest too deeply to analyse, are skipped (listed in `INDEX.md`, counted as `skipped`) but still counted and their comments read.
Generated files start with a `generated by code-library` marker; edit the source or the config, never the output.
